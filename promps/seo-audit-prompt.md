## Крок 1 — Розвідка (обовʼязкова перед аналізом)

Спочатку склади карту релевантних частин коду. Не аналізуй, просто знайди й перелічи:

1. **Layout-и та head:** усі Blade-layout-и (`resources/views/layouts/**`, `components/layouts/**`) — де формується `<head>`, `<title>`, meta-теги.
2. **Роути:** `php artisan route:list` — публічні (гостьові) маршрути: список вакансій, сторінка вакансії, сторінка компанії, статичні сторінки (`/about`, `/offer`, `/contacts`), головна.
3. **SEO-компоненти:** знайди наявні View Components / Volt-компоненти, повʼязані з SEO (зокрема `JobPostingSchema`).
4. **Конфіги:** `public/robots.txt`, наявність генератора `sitemap.xml` (роут, контролер, команда чи пакет).
5. **Моделі:** `Vacancy`, `Company`/`Employer`, що відповідають за слаги, статуси, `VacancyPublicationType`.

Виведи цю карту коротко перед тим, як переходити до аналізу.

## Крок 2 — Аудит за блоками

Для **кожного** пункту нижче зафіксуй статус, де перевіряв (файл/роут) і коротку рекомендацію.

### Блок A — Технічне SEO (індексація та краулінг)

- **robots.txt** — чи існує, чи коректний, чи містить посилання на `sitemap.xml`, чи не закриті випадково важливі розділи.
- **sitemap.xml** — чи генерується динамічно; чи включає вакансії, компанії, статичні сторінки; чи проставляється `lastmod`; **чи виключені прострочені та анонімні вакансії** (`VacancyPublicationType`, логіка `vacancies:refresh-anonymous`).
- **Канонічні URL** (`<link rel="canonical">`) — чи присутні на сторінці вакансії, компанії, у списках; **особливо на сторінках з фільтрами** (локація / зарплата / тип зайнятості).
- **Фасетна навігація** — як технічно реалізовані фільтри (query-параметри / Livewire-стан)? Чи індексуються комбінації фільтрів? Чи є ризик дублікатів і роздування краул-бюджету? Чи застосовано `noindex`/`canonical` до фільтрованих сторінок.
- **Пагінація** — як обробляється (canonical на першу сторінку / самопосилання / `noindex` на глибокі сторінки).
- **Meta robots / noindex** — де застосовується; **підтвердь, що прострочені вакансії мають `noindex`** (за памʼяттю — реалізовано в `JobPostingSchema`-флоу, перевір фактично).
- **HTTPS / редіректи** — чи є канонічний хост (www vs non-www), консистентність (з урахуванням Cloudflare Full Strict).

### Блок B — On-page

- **`<title>`** — чи унікальний і шаблонізований для кожного типу сторінки (вакансія / компанія / список / статична / головна); чи не статичний на всіх.
- **Meta description** — чи динамічна, чи задається пер-сторінково, чи не дублюється.
- **Open Graph + Twitter Card** — `og:title`, `og:description`, `og:image`, `og:url`, `twitter:card` — чи присутні (критично для шерингу вакансій у соцмережах/месенджерах).
- **Ієрархія заголовків** — рівно один `<h1>` на сторінку; логічна структура H2–H3.
- **URL / слаги** — структура маршрутів вакансій і компаній; чи семантичні слаги, чи числові id.
- **`<html lang="uk">`** — чи проставлено.
- **Alt-тексти** — на логотипах компаній і ключових зображеннях.
- **Внутрішня перелінковка** — чи є звʼязки вакансія ↔ компанія, хлібні крихти.

### Блок C — Структуровані дані (Schema.org JSON-LD)

- **JobPosting** (наявний `JobPostingSchema`) — перевір повноту полів: `title`, `description`, `datePosted`, `validThrough`, `hiringOrganization`, `jobLocation` (office/hybrid/remote), `baseSalary` (range), `employmentType`. Зафіксуй, чого бракує.
- **Organization** — чи є schema для компаній-роботодавців.
- **BreadcrumbList** — чи є розмітка хлібних крихт.
- **WebSite + SearchAction** — чи є розмітка для sitelinks search box на головній.
- Перевір валідність структури (відповідність типам Schema.org), не лише наявність.

### Блок D — Легальна відповідність індексованих текстів (п. 2.2 оферти)

- `grep` по індексованих текстах (`<title>`, meta description, `<h1>`, OG-теги, головна сторінка) на формулювання, що **натякають на посередницькі рекрутингові послуги**: «пошук вакансій», «пошук роботи», «підбір персоналу», «рекрутинг» тощо.
- Очікувана коректна термінологія: «Перегляд та фільтрація оголошень».
- Зафіксуй кожне порушення з точним розташуванням — це впливає і на легальність, і на SEO-копірайтинг.

## Крок 3 — Формат звіту

Збережи результат у `SEO_AUDIT_REPORT.md`. Для кожного пункту використовуй таблицю або список зі статусами:

- ✅ **Є** — реалізовано коректно
- ⚠️ **Частково** — є, але неповно / потребує доопрацювання
- ❌ **Відсутнє** — не реалізовано
- 🔴 **Проблема** — реалізовано, але працює некоректно / шкодить SEO

Для кожного запису вкажи:
1. **Статус** (значок вище)
2. **Розташування** (файл : рядок / роут / компонент)
3. **Знахідка** (що саме виявлено)
4. **Рекомендація** (1–2 речення)
5. **Пріоритет** (Високий / Середній / Низький)

Наприкінці звіту додай:
- **Зведення** — скільки пунктів у кожному статусі.
- **Топ-5 пріоритетних дій** перед повним запуском.

Після збереження звіту — **СТОП, без виправлень**.
